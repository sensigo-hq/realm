# Compatibility: what a release keeps, how a change is announced, and the road to 1.0

<!-- description: What a Realm release keeps working, how a change is announced, the record so far, and what comes before 1.0. -->

Realm's version starts with 0. From 0.50.0 on, every change to Realm follows one rule, in this order: keep what works working; where that cannot be done, give a migration guide and a tool that does the work; release a change that breaks what works only as a last resort, and then still with an easy way across; and for the odd case that neither covers, a specific remedy. This page says what that rule covers today, how a change reaches you, what has happened so far, and what is still to come before 1.0.

## What a release keeps

Two kinds of thing are outside Realm and depend on it: what you write and store (workflow files, the project file `realm.yaml`, registered workflows, the runs in `realm.db`, export files, the environment names Realm reads and the files under its home folder) and what you call (the CLI's commands, flags and exit codes; the MCP tools, the fields of their replies and the shape `tools/list` declares for a reply (`outputSchema`); `realm listen`'s addresses and reply fields; the store interface and its test kit; the library's exported names).

The CLI's commands, flags and exit codes, and the reply codes of `realm listen` and `realm serve`, are listed in one file in the repository, `packages/cli/src/inventory/kept-surface.txt`. The test suite regenerates that list from the code and fails when it differs from the file, and it fails too when an entry changed since the last release without a changelog line naming it — so a change to them is made on purpose, in the same change as the line that announces it.

The shape of `get_run_state`'s reply — every field and every word — is published as a JSON Schema in the repository, `docs/reference/mcp/run-state.schema.json`, built from the same lists the engine uses; every list in it is open and every object accepts a key it does not know, so a new word or field is never a breaking change. Added after version 0.50.0.

From 0.50.0 on, a change to any of these follows the rule above. A few things may still change in a minor release and are announced when they do: the exact wording of lines meant for a person to read (the CLI's human text, the `Disclosure:` line, the Slack post's text, the sentences the MCP replies carry for an assistant), and the library's exported names not tagged `@public` or `@beta`, on the main entry or any subpath (`@sensigo/realm-mcp`'s `./dist/tools/*.js` included); the API reports (`packages/core/src/inventory/api-report.txt`, `packages/mcp-server/src/inventory/api-report.txt`) list every name of the main entries and `./home`, each tagged declaration with its text; a `@beta` declaration may change in a minor release, named in the changelog, until it settles. A promised list of words — an exported list of literals, or a table keyed by them, that the API reports tag, such as `WAY_VERBS`, `UNAVAILABLE_CODES`, `STOP_KINDS` and `PARTIES`, and the types over them — may gain a member in a minor release, named in the changelog, and a type keyed by such a list (`WayRenderer`, one function per verb) gains the member with it; a program's switch over such a list keeps a default branch, and a program that renders ways builds its map with `PartialWayRenderer` completed by `withLibraryWords`, so a verb added later renders with Realm's words until the program writes its own; a program that writes the full `WayRenderer` itself adds a function when a verb is added. A script should read machine output where a command offers it (`--json`) and match a human line only when it has to; where it has to, the changelog names every change to such a line.

Stored data has its own guard. `realm.db` carries a format version. `realm db migrate` upgrades a file written by an older Realm, after a backup; an older Realm refuses a file written by a newer one with one line that says so, and changes nothing. From 0.50.0 the first migrate is a real step: it moves a 0.49.0 file from format version 1 to 2 ([A store version change](../guides/upgrade.md#a-store-version-change)). A home 0.50.0 creates, or that `realm run import` fills, is created at version 2 and needs no migrate. The version after 0.50.0 moves the file to format version 3, a 0.50.0 file in one step and a 0.49.0 file in two, in one migrate; a home it creates is created at version 3. A registered workflow keeps running as it was registered until you register it again; a new release's stricter checks apply at that registration, not before, except where the changelog says otherwise (so far 0.42.0's `trust` check, and the Slack answerer rule: a gate whose `owner` is not a Slack member ID can no longer be answered in its Slack thread, in a registered workflow as in a question open when you upgrade). Each release's export files and stored runs, and the shapes its loader gives the example workflows, are recorded from the published package into the repository (`packages/cli/src/corpus/<version>/`, from 0.49.0 on), and every later release's tests read them back and require the same shapes; a change that is meant lands as a reviewed exception file beside the artifact and is named in the changelog.

## How a change reaches you

A change to what a file may contain or means, to a command, a flag, an exit code, a reply field, an address, a store-interface member or an exported name ships in a minor release (0.x.0), never in a patch release, and the changelog's **Upgrading** section names it and what to write instead. From 0.50.0 on, a command, a flag or a key that is removed keeps answering for one more minor release with what replaced it, instead of failing as unknown; the changelog names the release it goes away in.

## Deprecations

When a release retires a flag, a key, a command or a reply field, Realm says so before it goes: one line on the error output, once per retired thing in a command's run — `Warning: [REALM-D001] …`, saying what you used, what it means now, what to write instead and the release it goes away in — never in the main output or in a `--json` document. A script that merges the two streams sees it; one that reads only the main output does not. Over the stdio MCP server, the same line goes to the server's error output and, unless the client set its log level above warning, to the protocol's log notification. A value read as the program starts, such as REALM-D001's, is said before any app connects, so its line goes to the error output only. The identifier never changes, and the changelog's Upgrading section names the release the thing goes away in.

| id         | since  | goes away     | what                                                       |
| ---------- | ------ | ------------- | ---------------------------------------------------------- |
| REALM-D001 | 0.50.0 | not scheduled | The gate-answers value offered was given.                  |
| REALM-D002 | 0.51.0 | 0.52.0        | A refusal that named no run's state carried run_version 0. |

## The record so far

Sixty-one releases, 0.1.0 (2026-06-01) to 0.50.0 (2026-11-17); eleven of them patch releases, none of which changed any of the above. What a correct workflow file does or may contain changed fifteen times, in six releases; eleven of the fifteen refused a file that was already wrong, each with a message saying what to write instead; one key was removed (0.14.0, `services.auth.token_from`; a file that still has it is refused with a message that says so). The library's exported names and the MCP replies' fields changed more often; the units below are what makes them easy to keep from here. These numbers are refreshed at each release.

## The road to 1.0

Before 1.0, each of these lands as its own change, in this order, so that keeping compatibility is a property of the code and its tests rather than of care: a place for deprecation warnings (the error output, once per retired thing in a command's run, so a script that reads the main output never sees one); a committed inventory of the CLI's commands, flags and exit codes, the environment names and `realm listen`'s reply fields, checked by a test; a corpus of each published release's stored shapes (export files, run records, workflow files) that every later release must still read, generated from the published packages at each release; the library's public interface tagged in the source, each declaration checked by a test, with the rest importable from the main entry until 1.0 and from an internal entry after; the run state's published schema; a published schema of the workflow file derived from the loader itself, and tightenings that apply to newly registered copies only; `--json` output with a format version on the `realm run` commands scripts read; a format field on the run record; a stated reading window for export files; and the store test kit's laws frozen per release for anyone who implements a store. Then 1.0 comes with its own written promise for the 1.x series.
