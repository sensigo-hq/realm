# Run state and health findings

<!-- The two counts in the first paragraph are written by scripts/generate-docs-tables.mjs from Realm's word lists, which also checks that the `next_actions_status` table and the findings section list exactly those words; the rows' words are written by hand. `get_run_state` returns where a run stands: its phase, its steps, what can be called next, and anything Realm finds wrong with it. This page lists every field of the reply, the 8 values of `next_actions_status`, and the 17 health findings, which `realm run inspect` and `realm run list --stuck` also report. Every reply shown came from a call.

For the tool's parameters, see [MCP tools](tools.md#get_run_state).

## The reply

For a run that is waiting at a gate:

```json
{
  "run_id": "7da561ee-5987-497d-83a5-1eded6dc9b63",
  "workflow_id": "triage",
  "run_phase": "gate_waiting",
  "terminal_state": false,
  "completed_steps": ["classify"],
  "in_progress_steps": ["draft"],
  "failed_steps": [],
  "skipped_steps": [],
  "pending_gate": {
    "gate_id": "00bb04f5-1bb7-4f38-91c5-14cdb17b3f0e",
    "step_name": "draft",
    "preview": { "reply": "We have refunded the charge." },
    "choices": ["send", "discard"],
    "opened_at": "2026-10-01T23:34:09.630Z"
  },
  "evidence_count": 2,
  "last_step": "draft",
  "created_at": "2026-10-01T23:34:09.429Z",
  "updated_at": "2026-10-01T23:34:09.635Z",
  "params": { "ticket": 101 },
  "next_actions": [
    {
      "instruction": {
        "tool": "submit_human_response",
        "params": {
          "run_id": "7da561ee-5987-497d-83a5-1eded6dc9b63",
          "gate_id": "00bb04f5-1bb7-4f38-91c5-14cdb17b3f0e"
        },
        "call_with": {
          "run_id": "7da561ee-5987-497d-83a5-1eded6dc9b63",
          "gate_id": "00bb04f5-1bb7-4f38-91c5-14cdb17b3f0e",
          "choice": "<send|discard>",
          "responded_by": "<the person's name, as they gave it; leave out if none>"
        }
      },
      "human_readable": "Human review required for step 'draft'. Ask the user to choose one of: send, discard, then call submit_human_response with their choice. The question's text, when its gate declares a message, is get_run_state's pending_gate.resolved_message. The conversation that opened the question passes back the claim_token it was given then, when it was given one. Pass the person's own name as responded_by when they gave one; never a guess.",
      "orientation": "Run is paused at gate '00bb04f5-1bb7-4f38-91c5-14cdb17b3f0e'."
    }
  ],
  "next_actions_status": "awaiting_human"
}
```

This read came from a server started with `--gate-answers permitted`. Under the default `asked`, and under `withheld`, the entry has `awaiting` in place of `instruction`, and `poll_after_ms` (and `until`, when the question has a deadline) are added. See [Gate answers over MCP](gate-answers.md). Added after version 0.47.0.

For the same run after it completed, `pending_gate` is gone and two fields are added:

```json
{
  "run_phase": "completed",
  "terminal_state": true,
  "terminal_reason": "Workflow completed.",
  "sealed_by_arm": "complete",
  "next_actions": [],
  "next_actions_status": "skipped_terminal"
}
```

## `next_actions_status`

| Value                   | Means                                                                                                                                                                                                                                                                                                                           | `next_actions`                                                                                                                                                                                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ok`                    | `next_actions` says what to do next.                                                                                                                                                                                                                                                                                            | The steps that can be called, then `advance_run` when the engine owes work beside them. It can be empty.                                                                                                                                                |
| `awaiting_human`        | A gate is open, and its time is not up — or it declares no `on_expiry`.                                                                                                                                                                                                                                                         | The question's answer, `submit_human_response`, without a `claim_token`, where the session has the answer tool (under `permitted`); under the default `asked` and under `withheld`, the await entry. Added after version 0.46.0, which leaves it empty. |
| `skipped_terminal`      | The run has ended.                                                                                                                                                                                                                                                                                                              | Empty.                                                                                                                                                                                                                                                  |
| `advance_owed`          | The only work that can run is the engine's: a guard is pending or an `auto` step can run here, or an open question's time is up and it declares `on_expiry`, which `advance_run` carries out first. Added after version 0.46.0, which says `auto_pending` and offers no act, and `awaiting_human` for an expired question.      | The one act, `advance_run`.                                                                                                                                                                                                                             |
| `blocked_on_capability` | An owed step needs a handler or an adapter that this server does not have, and nothing else is owed to the engine. A server judges with its own extensions (an empty set when it has no project extensions). A server that has it says `advance_owed`. Judging with the server's own extensions was added after version 0.46.0. | Empty, or the agent steps that are ready.                                                                                                                                                                                                               |
| `claim_stale`           | A step was started, did not finish, and is past its time, or no program held its claim's lease when it was checked (added after version 0.50.0).                                                                                                                                                                                | Any other steps that can be called.                                                                                                                                                                                                                     |
| `claim_unknown_age`     | A step was started and did not finish, Realm has no time limit for it, and nothing else can be called.                                                                                                                                                                                                                          | Empty.                                                                                                                                                                                                                                                  |
| `workflow_unresolved`   | The run's workflow cannot be read, so Realm cannot work out the next step.                                                                                                                                                                                                                                                      | Empty.                                                                                                                                                                                                                                                  |

When more than one applies, `awaiting_human` comes first, then `blocked_on_capability`, then `claim_stale`.

`ok` with an empty `next_actions` on an open run means one of three things, and `agent_action` says which (added after version 0.47.0). A held step can still finish: wait for it (`await`). Or every step it waits on is held by a claim whose deadline has passed, or whose lease no program held when it was checked (`report_to_user`): no result is recorded for them, and a person can free each one (both added after version 0.50.0). Or every step that could run next cannot (`report_to_user`): an `auto` step for an invalid `trust`, a failed precondition or an input its schema refuses — `engine_runnable` names each with `refused_by` and `refusal` — or an agent step for an invalid `trust` or a failed precondition — `agent_refused` names it the same way, and it is never offered in `next_actions` (agent steps added after version 0.46.0). Waiting does not help then: for a refused `trust` or precondition the run cannot go on until the workflow is corrected and registered again (the run picks up the corrected definition), or it is ended with `abandon_run`; for a step refused for its input, a new run with params that fit (when the step has no `depends_on`: the engine gives it the run's params), or a corrected `input_schema`. For a step that builds its input with an `input_map` (one with a `handler` or a `uses_service`), its schema checks what the map builds: a corrected `input_map` or `input_schema`, or a new run with params that fit when the key its schema refuses is built from `run.params`. Every reply that says what comes next ends with that way out — the reply of the step or the answer that left the run there, `start_run`'s creation reply, and `advance_run`'s reply, which runs nothing: `Correct the workflow and register it again, then call advance_run; or end the run with abandon_run.`, or, with a step refused for its input, each step's own way and then the run's ([MCP tools](tools.md#advance_run); added after version 0.46.0). A step refused for its handler or adapter also says what it was judged from, in `basis` (added after version 0.46.0): `registry` — the server's own extensions lack it (`refusal`: `handler '<name>' is not registered here`). Every server judges this way: one with no project extensions has an empty set of them. Only a caller that passes no extensions at all — a program that embeds the engine — judges by the run's `capability_blocks` record of the last attempt: `basis` `marker`, `refusal` `handler '<name>' was not registered in the runner that last attempted it`. With neither, `runnable_here: "unknown"`. A guard that is ready and that no write has decided is owed work: the status is `advance_owed` and `next_actions` holds `advance_run` (see `guard_awaiting_settlement` below). This paragraph describes behaviour added after version 0.46.0.

## `include_steps`

`include_steps`, and the `steps` and `drive_failure_costs` fields it adds, were added in 0.46.0. So was the record of what a failed drive was billed. So were `step_claims`, `driven_by` and `answers`.

`step_names` and `cursor` were added after version 0.48.0. With `step_names`, `steps` holds only the named steps that ran; a name the run has not attempted is named in `warnings` (`'<name>' is not a step this run has attempted`, ten named, then how many more). When the reply would pass the 40,000-character ceiling and no list before the steps' detail, nor leaving out `params`, can make it fit by itself — the steps' detail is cut last ([the ceiling](tools.md#the-reply)) — `steps` keeps its first steps in the order they were first attempted, `steps_more` says how many it left out and `next_cursor` names the last one shown: call again with `cursor` set to it, and the same `include_steps` or `step_names`, for the next page. The cursor is a place in the run's order of first attempts, and `step_names` picks from what follows it. A page with nothing after the cursor has no `steps` and no `next_cursor`. A `cursor` without `include_steps: true` or `step_names`, or naming no step the run has attempted, is refused with `VALIDATION_CURSOR`.

With `include_steps: true`, the reply has a `steps` object with one entry for each step that ran. It holds each step's attempts and their cost, not its evidence entries, so it does not show where a bare `auto` step's output came from (`output_source`); `realm run inspect` shows that, and so does the run's record:

```json
"steps": {
  "classify": {
    "attempts": [
      {
        "attempt": 1,
        "status": "success",
        "cost": {
          "requests": 1,
          "basis": "unobservable",
          "state": "unobservable",
          "prompt": { "value": 412, "reported": 1, "of": 1, "only_request_index": 0 },
          "output": { "value": 38, "reported": 1, "of": 1, "only_request_index": 0 },
          "models": { "names": ["claude-sonnet-5-5"], "reported": 1, "of": 1 },
          "cache_requested": {
            "entries": [
              {
                "value": "lifetime",
                "lifetime_s": 300,
                "ttl_sent": false,
                "source": "runner_default",
                "by": "realm agent",
                "auto": { "basis": "step_gaps", "gaps_s": [] }
              }
            ],
            "reported": 1,
            "of": 1
          }
        }
      }
    ]
  }
}
```

A reclaim's audit entry (a person's `realm run reclaim`, or `realm agent` taking a step back) is not an attempt: it is not in `attempts` and `run_cost` does not count it, and a step whose only entries are reclaims has no entry in `steps`, so naming it in `step_names` puts it in `warnings` (added after version 0.50.0, which counted each as an attempt).

## Failure text

When a step or a drive fails, `get_run_state` shows the words the failure came with: a provider's error message, the text a handler threw, an adapter's reply. A provider can repeat text from the request in its error, and a handler's error can carry the data it was working on. A server started with `--failure-text hidden` (`realm mcp`, `realm serve`), with `REALM_MCP_FAILURE_TEXT=hidden`, or by a program that passes `failureText: 'hidden'` to `createRealmMcpServer` shows an assistant those words' length in their place, as `‹string, N characters›`, N the length of the text on the record. The default is `shown`; when more than one is set, `hidden` wins. Added after version 0.50.0.

| `failures[].message`                                                           | `‹string, N characters›`, N the recorded text's length, also when it is over 500 characters                                                                                                                                                                                            | `step`, `code`, `category`, `stop_reason`, `agent_action`, `failure_kind`, `attempt` and `unknown` |
| `drive_failures.entries[].message`                                             | `‹string, N characters›`                                                                                                                                                                                                                                                               | The time, the step, the provider, `error_class`, the status, the attempts and what was billed      |
| The `drive_failing` finding's `reason` in `run_health`                         | Realm's sentence, with the message as its shape: `the last drive attempt failed <when> (<error_class>): ‹string, N characters›`                                                                                                                                                        | The finding's `evidence`                                                                           |
| `abort_context.abort_message`                                                  | `‹string, N characters›` when a handler aborted the run                                                                                                                                                                                                                                | `step_id`                                                                                          |

| `not_priced[].detail` (under `include_steps`)                                  | `‹string, N characters›` when the project's code threw while it was loaded                                                                                                                                                                                                             | Its `cause` and `count`                                                                            |
| `terminal_reason`                                                              | Realm's words, with the failure's as their shape: `Step '<step>' failed: ‹string, N characters›`; `Handler '<step>' aborted the run: ‹string, N characters›`; with more than one failed step, `<count> steps failed: <step> ("‹string, N characters›"), …`, each step's message shaped | `sealed_by_arm`, `failed_steps` and `failures`                                                     |

Inside these fields, Realm's own words are shaped with the failure's: in `terminal_reason`, a retried step's `Step '<step>' failed after <N> attempts`; in `failures[].message`, a guard's `Guard resolution error: unresolvable path …`. Which sentence `terminal_reason` holds is read from how the run ended (`sealed_by_arm`); a run sealed before Realm recorded that is placed by the form of its reason. A reason Realm cannot place is shaped whole, and so is its `abort_context.abort_message`. A `terminal_reason` that holds no failure's words stays as it is: a completed run, a run abandoned with a person's reason, a gate's expiry, a guard's resolution error with one failed step, `spawn_failed` and `extensions_load_failed`. A guard's abort message is the workflow author's own, and stays. The run's record and `realm run inspect` keep the words.

A reply in which something was shaped says so in its `disclosure` receipt: `failure_text: "withheld"`, with the shaped fields' paths in `shaped`. A run with no failures carries neither.

The setting also covers the replies of the assistant's own calls (`execute_step`, `advance_run`, `start_run`, `submit_human_response`, `start_run_batch` and `present_question`): when a step fails, except because its answers were refused too many times (`VALIDATION_EXHAUSTED`, Realm's own sentence, which stays), `errors[0]` shows as `‹string, N characters›`, and `error_details` keeps its top-level keys, a retried step's `stepName`, `attempts` and `exhausted_by`, and any number in `status` or `retry_after`, and shows every other value as its shape; a handler's abort shows `Handler step '<step>' aborted the run: ‹string, N characters›` in `context_hint`; `start_run_batch`'s `started[].terminal_reason` shows as `terminal_reason` does here. A refusal of the call itself is Realm's own sentence and stays. When a workflow's code throws while it is loaded, the loader's message, which quotes what the code threw, shows as its shape in `errors[0]` and in `not_priced[].detail`; `error_code`, `agent_action` and `context_hint` stay, and so does a sentence Realm wrote about the project, such as a handler with no `execute`, a `use:` that is missing or names no export, or a module file that is not there. An invalid `realm.yaml`, or a secret it names that is not set, shows as its shape whatever the setting: Realm then cannot read the declared secrets, so the reply shows its values as their type and size (`declared_cause: load_failed`). A program's own `registryProvider` is judged the same way: a `WorkflowError` it throws stays as written, and anything else it throws shows as its shape. Text a workflow copies into a question, a prompt or an output is shown as that field always is.

## Health findings

A finding is one thing Realm has noticed about a run that someone may need to act on. Each has a `kind`, a `reason`, and where they apply a `step`, a `since` time and `evidence`.

```json
"run_health": [
  {
    "kind": "drive_failing",
    "step": "classify",
    "reason": "the last drive attempt failed 17m ago (2026-10-01T21:09:36Z) (connection_error): Connection error.",
    "evidence": {
      "step": "classify",
      "error_class": "connection_error",
      "at": "2026-10-01T23:21:18.899Z",
      "total": 1,
      "first_failed_at": "2026-10-01T23:21:18.899Z",
      "derived_ceiling_ms": 1861500
    }
  }
```

| `cannot_go_on`                 | The run is in `running`, no step is in progress, and a step it must run next is refused before its claim — its trust, a precondition, or an input its schema rejects — so nothing can run until the workflow is corrected. (added after version 0.47.0)                                                                      | `<step>=cannot_go_on(<check>) (realm run inspect <run-id>)`                                                                                   |
| `owed_undriven`                | The run is in `running`, no step is in progress, the engine owes work — a guard to decide or an `auto` step to run — and the run has not changed for a minute (`realm run list --older-than` moves the limit). `realm run advance <run-id>` runs what is owed, when the code it loads has the step's handler. A step that `realm agent` must run is not the engine's: a run waiting for it gets no such finding. A ready guard also shows `guard_awaiting_settlement`. A failed drive counts as a change, so after one the finding waits another minute; the run then also shows `drive_failing`. Added after version 0.50.0. | `<step>=owed_undriven (realm run advance <run-id>)`                                                                                           |
| `drive_failing`                | The last thing that happened to the run was a failed drive by `realm agent`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | `<step>=drive_failing(<kind>)`; `drive_failing(<kind>)` alone when the failure named no step (added after version 0.50.0)                     |
| `stale_claim`                  | A step is in progress past its time, or for an unknown time, or no program held its claim's lease when it was checked, and the run is in `running`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | `<step>=claim_stale` or `<step>=claim_unknown_age`                                                                                            |
| `wedged_gate_sibling`          | The same, in a run that is waiting at a gate, for a step other than the gate's.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | `<step>=claim_stale` or `<step>=claim_unknown_age`                                                                                            |
| `capability_block`             | A step needs a handler or an adapter that the process which tried it did not have. `get_run_state` leaves the finding out for a step its own server can run (the record stays in `capability_blocks`); `inspect` and `list --stuck` read the record alone. Leaving it out was added after version 0.46.0.                                                                                                                                                                                                                                                                                                                     | `<step>: needs handler '<name>'`                                                                                                              |
| `gate_expired_awaiting_drive`  | A gate's time has passed and nothing has yet carried out what was declared for it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | `<step>=gate_expired(<on_expiry>) (realm run advance)`, or `<step>=gate_expired(finding_only) (realm run respond)`                            |
| `guard_awaiting_settlement`    | A guard step is ready, and no write has decided it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | None. It does not select a run: `advance` can decide the guard. (added after version 0.47.0)                                                  |
| `trust_value_invalid`          | A step that is ready has a `trust` value Realm does not accept. The registered copy was stored by an older version.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | None. It does not select a run; when nothing else can run, the run is also `cannot_go_on`, whose label is shown. (added after version 0.47.0) |
| `definition_unresolvable`      | The run's registered workflow cannot be read.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | `definition_unresolvable (<why>) (realm run inspect <run-id>)`                                                                                |
| `gate_corruption`              | The run's record says a gate is both answered and open.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | `<step>=gate_corruption`                                                                                                                      |
| `structured_output_downgraded` | A step asked for `structured_output: strict` and ran without it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | None. It does not select a run.                                                                                                               |

Findings about a run that has ended:

| `kind`                        | Found when                                                                                 | Label in `list --stuck`               |
| ----------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------- |
| `terminal_pending_finalizer`  | The run still owes a cleanup step.                                                         | `<step>=<state> (realm run drain)`    |
| `completed_with_failed_steps` | The run completed, and one of its steps had failed.                                        | None. It does not select a run.       |
| `terminal_with_stale_gate`    | The run's record still holds an open gate. Only records written by old versions have this. | `<step>=stale_gate (realm run purge)` |

`structured_output_downgraded` is also found on runs that have ended.

`record_stamped_ahead` is found on any run, open or ended: the run's last change is stamped more than 5 seconds after the clock of the program reading it, so one of the two clocks is off, and the finding cannot tell which. Its `evidence` holds `record_updated_at`, `reader_at` (the reader's own clock) and `delta_ms`. It does not select a run in `list --stuck`. Added after version 0.48.0.

### Examples

`never_claimed_idle`, for a run that had not changed for two days:

```json
{
  "kind": "never_claimed_idle",
  "reason": "parked with no claimed step, idle",
  "since": "2026-09-29T23:39:44.004Z",
  "idle_ms": 172815275,
  "evidence": { "idle_threshold_ms": 86400000, "eligible_steps": ["a"] }
}
```

`cannot_go_on`, for a run whose step `publish` needs a `text` input that its earlier step did not return (added after version 0.47.0):

```json
{
  "kind": "cannot_go_on",
  "step": "publish",
  "reason": "input_schema",
  "since": "2026-10-16T10:53:51.116Z",
  "evidence": {
    "refused": [
      {
        "step": "publish",
        "check": "input_schema",
        "refusal": "Invalid input for step 'publish': the input must have required property 'text'"
      }
    ]
  }
}
```

`stale_claim`, for a step whose process was killed, 15 minutes after the step started. The reply also has `"next_actions_status": "claim_stale"` and the same step under `stuck_claims`:

```json
{
  "kind": "stale_claim",
  "step": "fetch",
  "reason": "claim_stale",
  "evidence": { "state": "claim_stale", "deadline": "2026-10-01T23:53:39.499Z" }
}
```

When Realm has no time limit for the step and its claim names no lease, `reason` and `evidence.state` are `claim_unknown_age`, `deadline` is `null`, and the finding is there from the start. `evidence.deadline_absent` then says why there is no time limit — `step_not_auto`, `finalizer_bearing`, `not_recorded` (a claim written before this field was added or by a store that does not write it, or a step in progress with no claim record), or the word another store wrote (added after version 0.50.0). A step a `realm agent` drive holds names a lease: there is no finding while its program holds the lease, `claim_stale` once no program holds it, and `claim_unknown_age` when its lease file is gone or the lease could not be checked (added after version 0.50.0).

`wedged_gate_sibling`, for the same in a run that is waiting at a gate on another step. `next_actions_status` stays `awaiting_human` — until the gate's time is up when it declares `on_expiry`; the status is then worked out as for a run with no gate, so a step past its time makes it `claim_stale` (added after version 0.46.0):

```json
{
  "kind": "wedged_gate_sibling",
  "step": "fetch",
  "reason": "claim_stale",
  "evidence": { "state": "claim_stale", "deadline": "2026-10-01T23:53:41.736Z" }
}
```

```json

  "step": "limit",
  "reason": "guard 'limit' is eligible and has not been settled"
}
```

A guard is decided inside the write that makes it ready: a step that finishes, an answer to a gate, or a gate whose time runs out. This finding is about a guard that became ready some other way. That is a guard that is ready when the run is created by `start_run_batch` or by a program, as here, or when `realm run resume` opens the run again at a failed guard. Such a guard is decided by the run's next finished step or gate answer, or by `advance_run`, which `next_actions` names. A call to the guard or to the step after it is refused as not eligible. A run that `start_run` creates never has this finding: `start_run` decides such a guard itself. Both were added after version 0.46.0.

## The schema

<!-- run-state.schema.json and run-state.added-after.json are written by scripts/generate-run-state-schema.mjs from the built mcp-server; a test regenerates them and fails when they differ. After `npm run build`, run `npm run docs:schema`. -->

`get_run_state`'s reply is described by `docs/reference/mcp/run-state.schema.json` in the repository, a JSON Schema (draft 2020-12) built from the same word lists the engine uses, so the file and the code cannot drift: a test regenerates it and fails when they differ. Every list in it is open and every object accepts a key it does not know. The cost view (`steps.*.attempts[].cost`, `steps.*.total`, `run_cost`, `drive_failure_costs[].cost`, and a drive failure's `usage` and `model_attempts`) is described loosely until a later release. Added after version 0.50.0.

The file describes both replies: the run's state, and a refusal (for example, the run is not found). Every field in it is kept under the rule of [Compatibility](../compatibility.md), so a new word or field is never a breaking change. When Realm withholds values (the receipt's `values` is `withheld`), a number or true/false inside `steps` can arrive as its shape, a string such as `‹number›`; the schema allows it.

A program that reads the reply must accept a word it does not know in any list, and a key it does not know in any object. For a word it does not know, it acts as for the most cautious word of that list:

| The list                                                                                            | What a word it does not know means                      |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `next_actions_status`                                                                               | Act as for `report_to_user`.                            |
| `agent_action`                                                                                      | Act as for `report_to_user`.                            |
| `stop_reason`, `exhausted_by`                                                                       | Act as for `non_retryable`: do not retry.               |
| `error_code`, `error_category`                                                                      | The error is not retryable: report it.                  |
| `run_phase`                                                                                         | Read `terminal_state` for whether the run ended.        |
| `run_health[].kind`                                                                                 | A finding to show the person.                           |
| `stuck_claims[].state`                                                                              | The step is stuck.                                      |
| A status word                                                                                       | Not a success.                                          |
| A skip's `kind` or `rule`                                                                           | The step did not run.                                   |
| A drive failure's `error_class`                                                                     | The drive failed.                                       |
| A seal arm (`sealed_by_arm`)                                                                        | How the run ended is not verified.                      |
| `poll_reason`                                                                                       | Poll as for `fixed`.                                    |
| `on_expiry`                                                                                         | The question may end without an answer: ask the person. |
| The receipt's words (`declared`, `declared_cause`, `environment`, `question`)                       | Treat the value as withheld or unverified.              |
| An absence cause, an admission word or a class word (`absent_cause`, `admitted_by`, `by_source`, …) | The fact is unknown.                                    |

`docs/reference/mcp/run-state.added-after.json` says the release each field and each word arrived after: `"0.50.0"` marks what was there when the file was first published. A path in it is dotted keys, with `[]` for a list's entries and `.*` for a map's values (`steps.*.attempts[].status`), and `described_loosely` names the fields the schema does not yet describe in full. It is a file of its own because a validator in strict mode, Ajv's default, refuses a keyword it does not know, so a release marker inside the schema would stop such a client from using it.
