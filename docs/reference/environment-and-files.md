# Environment variables and files on disk

<!-- description: Every environment variable Realm reads, and every file and folder it reads or writes, both under ~/.realm and in a project. -->

This page lists every environment variable Realm reads, and every file and folder it reads or writes: under `~/.realm`, and in a project. The variable list comes from a search of Realm's code for each place it reads the environment. The file list comes from the code and from a listing of a home after one command.

Realm reads other variables by names that you give it:

| Named by                                                                                                | Read by                       | Used as                                                                        |
| ------------------------------------------------------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------ |
| `secret_from` in a workflow's [`trigger`](workflow/webhook-trigger.md)                                  | `realm listen`                | The secret that webhook requests are checked against.                          |
| `${secret:NAME}` in `realm.yaml`, when `secrets.sources` has `env`                                      | Every command that runs steps | The secret's value. See [Deployment manifest](deployment-manifest.md#secrets). |
| `'${NAME}'` in the `env` of an agent profile's [tool server](workflow/services-profiles-and-context.md) | `realm agent`                 | A value handed to the tool server it starts.                                   |

`realm agent` also reads the values of the variables in its environment, so that it can replace them, and the forms [Give an agent step tools](../guides/agent-tools.md#4-read-what-was-recorded) lists, with `[REDACTED]` in tool results, in error messages and in the prompt the agent step sends the model. It leaves some values alone: see [Give an agent step tools](../guides/agent-tools.md#4-read-what-was-recorded).

These are read by libraries that Realm uses, and change what Realm does (the `.env` loader reads a few more `DOTENV_CONFIG_*` variables; see [its documentation for the version Realm uses](https://github.com/motdotla/dotenv/blob/v17.4.2/README.md)):

| Variable                 | Read by            | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------ | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `OPENAI_BASE_URL`        | OpenAI's client    | Sends `realm agent`'s OpenAI requests to another address.                                                                                                                                                                                                                                                                                                                                                                                        |
| `ANTHROPIC_BASE_URL`     | Anthropic's client | Sends `realm agent`'s Anthropic requests to another address. A service there that refuses the request to cache with a 400 saying `cache_control` is not allowed is sent that request again without Realm's cache fields; when that works, every later request of the drive goes without them, and `realm run inspect` says so. A refusal in other words still makes each agent step fail: use `--prompt-cache off` (added after version 0.47.0). |
| `DOTENV_CONFIG_PATH`     | The `.env` loader  | The file loaded in place of `.env` in the current folder. See below.                                                                                                                                                                                                                                                                                                                                                                             |
| `DOTENV_CONFIG_OVERRIDE` | The `.env` loader  | Lets the `.env` file replace variables already set: any non-empty value, `false` and `0` included.                                                                                                                                                                                                                                                                                                                                               |

### The `.env` file in the current folder

When any `realm` command starts, it loads a file named `.env` from the folder it is started in, and adds each line to its environment. A variable that is already set keeps its value, unless `DOTENV_CONFIG_OVERRIDE` is set to any non-empty value (`false` and `0` included) in the environment the command starts with; a `DOTENV_CONFIG_PATH` or `DOTENV_CONFIG_OVERRIDE` line inside a `.env` does not change how that file is loaded. With `DOTENV_CONFIG_PATH` set, that file is loaded instead:

```bash
DOTENV_CONFIG_PATH=/etc/realm/serve.env realm serve
```

With `REALM_SERVE_TOKEN` only in that file, `realm serve` started. Without the variable, started in a folder with no `.env`, it stopped with `Error: REALM_SERVE_TOKEN is not set.`

This is separate from the `.env` beside `realm.yaml`, which holds a project's secrets and is read only for `${secret:NAME}`. In a project folder the two are the same file.

## Files under `~/.realm`

Every `realm` command and the `realm-mcp` server keep their data in one SQLite file in the Realm home. The first command on a new home creates the home folder, the store file and four fence files:

| Path                                     | Holds                                                                                                                                                                                                                                                                                      | Written by                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| `realm.db`                               | The store: runs with their evidence, refused answers, trace lines and sealed lines; the registered workflows; saved replays; `realm listen`'s duplicate-webhook marks. Created owner-only (mode 0600).                                                                                     | Every command and tool that opens its stores |
| `realm.db-wal`, `realm.db-shm`           | SQLite's write-ahead log and its index, beside the file while a process has the store open. A Realm that exits normally leaves none behind; after a crash, the next Realm that opens the store replays the log, and the files go when it exits.                                            | SQLite                                       |
| `runs`, `workflows`, `replays`, `dedup`  | Four read-only fence files (mode 0444), a few lines of text each, at the names the old JSON store's folders had. A Realm from before the SQLite store that is pointed at this home fails on them at once instead of starting a second store. Do not delete them while Realm uses the home. | The first open of the home                   |
| `.realm-fence-<name>-<pid>-<random>.tmp` | A fence file being placed; it exists for the length of one write. One left behind by a process that was killed can be deleted when no Realm process is running.                                                                                                                            | The first open of the home                   |

Never delete, move or replace `realm.db` or its side files while a Realm process is running. `realm db backup <path>` writes its copy outside the home; a backup that was killed may leave files whose names begin `<path>.part-` beside its target, which you can delete.

### The clock a run's times come from

The store stamps the times it writes, such as a run's `created_at` and `updated_at`, with this computer's clock. A Realm home on a folder that several computers share is not supported: each computer would stamp with its own clock.

A folder with a `.realm-test-clock` file is a test home. Only `@sensigo/realm-testing` creates one, for tests; the store only reads the file. A store opened there takes the time from that file when it creates a run, starts a step, writes a run with `update`, records a step's result or reads a run, so every process that opens the folder reads the same time (added after version 0.48.0). The file names the folder it was made for: a store opened on a copy of it in another folder refuses with `STATE_TEST_CLOCK_FOREIGN`. To use the copy as an ordinary store, delete its `.realm-test-clock` file.

The `realm` command and the `realm-mcp` server say once, on standard error, that they opened a store at a test location, on their first read of it: `this store runs on a test clock, now 2030-01-01T00:00:00.000Z`, with that read's time. An MCP reply judged on a test clock says so in its `basis`: `as_of_basis: "test_clock"` (added after version 0.48.0).

### Which commands remove data

| Command           | Removes                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `realm run purge` | An ended run: its record and evidence, its refused answers, trace lines and sealed lines — rows in `realm.db`. The space goes back to the file (the force line says by how much). Text of a deleted run may stay readable in the file's free pages and in `realm.db-wal` until the file is vacuumed and checkpointed, which the purge does when no other process is using the file. |

A duplicate-webhook mark expires at the end of its window; `realm listen` removes up to 100 expired marks of a workflow each time it records a new one. Nothing removes a registered workflow or a saved replay. Realm keeps runs until `realm run purge` removes them.

## Files in a project

Realm reads these, and writes none of them:

| File                                  | Holds                                                                            | See                                                                         |
| ------------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `workflow.yaml`                       | A workflow. A workflow's folder is the folder this file is in.                   | [Workflow file: top-level fields](workflow/top-level-fields.md)             |
| `profiles/<name>.md`                  | An agent profile, beside the workflow file unless `profiles_dir` says otherwise. | [Services, profiles and context](workflow/services-profiles-and-context.md) |
| The files named by `extensions`       | The project's own code.                                                          | [Project extensions](project-extensions.md)                                 |
| The files named by `workflow_context` | Text given to agent steps.                                                       | [Services, profiles and context](workflow/services-profiles-and-context.md) |
| `fixtures/*.yaml`                     | Tests for the workflow.                                                          | [Test a workflow](../guides/test-a-workflow.md)                             |
| `realm.yaml`                          | The project's settings, in the project's top folder.                             | [Deployment manifest](deployment-manifest.md)                               |
| `.env`                                | The project's secrets, beside `realm.yaml`.                                      | [Deployment manifest](deployment-manifest.md#secrets)                       |
| `package.json` or `.git`              | Marks the project's top folder.                                                  | [Deployment manifest](deployment-manifest.md#where-realm-looks-for-it)      |

Realm writes into a project in two cases:

| Command                      | Writes                                                                                                                                                                                |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `realm workflow init <name>` | A folder `<name>` with `workflow.yaml`, `schema.json`, `.env.example`, `README.md`, `registry.sample.js` and `realm.yaml`; inside a project, without `.env.example` and `realm.yaml`. |
| `realm run export <run-id>`  | `<run-id>.realm.json` in the current folder, or the file given with `--out`.                                                                                                          |

## A store other than `realm.db`

Every `realm` command and the `realm-mcp` server use the SQLite store in the Realm home. A program that calls Realm as a library can keep runs in a store of its own. See [Core library](core-library.md).
