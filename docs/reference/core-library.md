# Core library: stores and the store contract

<!-- description: Use @sensigo/realm as a library: the functions that run a workflow, the stores Realm ships, the store interfaces, and how to check a store of your own. -->

`@sensigo/realm` is the engine as a library. A program of your own can use it to run workflows without the `realm` command, and to keep runs somewhere other than files on disk. This page covers the functions that run a workflow, the stores Realm ships, the store interfaces, what a store of your own must do, and how to check that it does. Every output shown came from a program run against the built packages.

The package exports more than 200 values. This page covers the ones named above. Most of the rest are the parts the `realm` command is built from.

| Package                       | Holds                                                            |
| ----------------------------- | ---------------------------------------------------------------- |
| `@sensigo/realm`              | The engine, the loader, the file stores, the built-in adapters.  |
| `@sensigo/realm-mcp`          | The MCP server, as a function you can call with your own stores. |
| `@sensigo/realm-testing`      | An in-memory run store, and the tests for a store of your own.   |
| `@sensigo/realm-store-sqlite` | The Realm home: the SQLite store every `realm` command uses.     |

All four are ES modules and need Node 22 or later; `@sensigo/realm-store-sqlite` needs Node 22.22.3 or a later 22.x release, or Node 24.15.0 or later.

## Run a workflow from your own program

```js
import { openRealmHome } from '@sensigo/realm-store-sqlite';
import {
  loadWorkflowFromFile,
  createDefaultRegistry,
  executeChain,
  submitHumanResponse,
  deriveRunPhase,
} from '@sensigo/realm';

const { runStore: store } = await openRealmHome();
const definition = loadWorkflowFromFile('flow/workflow.yaml');

const registry = createDefaultRegistry();
registry.register('handler', 'refund_amount', {
  id: 'refund_amount',
  async execute(inputs, context) {
    return { data: { amount: context.run_params.total / 2 } };
  },
});

const dispatcher = async (stepName, input) => input;

const { record: run } = await store.create({
  workflowId: definition.id,
  workflowVersion: definition.version,
  params: { total: 40 },
});

let reply = await executeChain(store, definition, {
  runId: run.id,
  command: 'price',
  input: {},
  dispatcher,
  registry,
});
reply = await executeChain(store, definition, {
  runId: run.id,
  command: 'decide',
  input: { refund: true },
  dispatcher,
  registry,
});
reply = await submitHumanResponse(store, definition, {
  runId: run.id,
  gateId: reply.gate.gate_id,
  choice: 'approve',
  registry,
});

deriveRunPhase((await store.get(run.id)).record); // 'completed'
```

The workflow has an `auto` step `price`, then an agent step `decide` with a gate. Each call returned:

| Call                        | `status`           | `run_phase`    | Also                                     |
| --------------------------- | ------------------ | -------------- | ---------------------------------------- |
| `executeChain` for `price`  | `ok`               | `running`      | `data` is `{"amount":20}`                |
| `executeChain` for `decide` | `confirm_required` | `gate_waiting` | `gate.choices` is `["approve","reject"]` |
| `submitHumanResponse`       | `ok`               | `completed`    |                                          |

The replies are `EngineReply`: the fields of an MCP tool reply (see [MCP tools](mcp/tools.md)) without `next_actions`, `agent_action` and `blocked_reason.suggestion`, and with what can be done next as data — `ways` (each a call a program can make: `respond`, `run_step`, `advance`, `inspect`, `abandon` or `register`, with what it needs), `unavailable` (what cannot be done now: a `code`, its `facts`, and the ways that lead on, `remedy`), `basis` (the record and the moment they were judged on), `refusal` (the call's own refusal) and, on an error, `intrinsic_action` and `error.remedy` (added after version 0.47.0, whose replies were the MCP tool reply, `ResponseEnvelope`). A program reads the run with `store.get(runId)`, which returns `{ record, at }` (added after version 0.48.0), and takes a way with the function that matches it: `executeStep` for a `run_step` way, `advanceRun` for an `advance` way, `submitHumanResponse` for a `respond` way; `LIBRARY_WORDS` says each way in those words. `judgedSnapshotOf(reply)` returns the `{ record, at }` a reply was judged on: `at` is the reply's `basis.as_of`, and the record's `version` its `basis.run_version` (added after version 0.48.0). A program that writes words about a reply after the call judges them on it, and does not read the run again. It is kept beside the reply, never in it: a copy of the reply (`{ ...reply }`, `structuredClone`, or the reply sent as JSON) has none, and for a copy, or for a reply about a run the call could not read, it returns `undefined`. When a call carries out an expired question's `on_expiry`, the library prints nothing: the line that says so is in the reply's `warnings`, and names the call — for your program's own call, the function: `this advanceRun call first carried out its declared …` (`enacted_via: advanceRun`), and likewise `executeStep`, `executeChain`, `submitHumanResponse` and `executeEngineStep` (added after version 0.46.0, which also printed it to stderr, and whose `executeStep`, `executeChain` and `submitHumanResponse` said `execute_step` and `submit` there). Each of these functions takes a `caller` option for a host that names the call itself; see below.

Answering a question does not run an `auto` step that comes after it. Say the workflow has one more step, `file` (`execution: auto`, `depends_on: [decide]`). Then `submitHumanResponse` replies `status: ok` with `run_phase: running`. Its `context_hint` says `Gate 'decide' resolved with choice 'approve'.`, and its `ways` hold an `advance` way whose `owed` names `file`. Your program then calls `advanceRun` (also imported from `@sensigo/realm`), which runs `file`:

```js
reply = await advanceRun(store, definition, { runId: run.id, registry });
deriveRunPhase((await store.get(run.id)).record); // 'completed'
```

This form of `advanceRun` was added after version 0.46.0. The `Owed to the engine` sentence that followed the hint is the MCP door's since version 0.47.0; the library's reply says it with the `advance` way.

### The options of `executeChain` and `executeStep`

| Option       | Required       | Holds                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------ | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `runId`      | Yes            | The run.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `command`    | Yes            | The step's name.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `input`      | Yes            | For an agent step, the answer. For an `auto` step, `{}`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `dispatcher` | For some steps | A function Realm calls for the step `command` names when it is an agent step, or an `auto` step with neither `uses_service` nor `handler`. It is also called for a step whose `execution` is missing or unknown. It is required for each of these steps: without it the call rejects with `VALIDATION_OPTION_INVALID` before anything is read or written; given for any step, it must be a function (added after version 0.47.0). What it returns, as a plain value or through a promise, is recorded as the agent step's answer, or as that `auto` step's output. `executeChain` does not call it for the steps it runs after that one. The one above returns the input. |
| `registry`   | No             | The adapters and handlers the steps can use. Without it, only the `filesystem` adapter and the `check_quotes` handler.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `caller`     | No             | The call the expiry line names when this call carries out an expired question first. `executeStep` takes `executeStep` (the default) or `agent`; `executeChain` takes `executeChain` (the default), `execute_step`, `agent` or `run`. Any other value rejects with a `WorkflowError` with the code `VALIDATION_CALLER_INVALID` before anything is read or written. Added after version 0.46.0.                                                                                                                                                                                                                                                                            |
| `disclosure` | No             | The values your program hides, as a set from `buildDisclosureSet`. A gate this call opens stores its question masked with it, and cut to the view budget of 600 characters when the set knows every declared value; without it the question is stored as rendered and never cut. `advanceRun` and `executeEngineStep` take it too. Added after version 0.48.0.                                                                                                                                                                                                                                                                                                            |

A call judges an open question's expiry by its store's clock: it carries out an expired question's declared `on_expiry` first only when the question's time is up at the store's reading (the `now` option that set this time is removed after version 0.48.0).

`executeStep`, `executeChain` and `submitHumanResponse` answer a run they cannot read with an error reply, never a throw (`submitHumanResponse`'s names `command: submit_gate`): `STATE_RUN_NOT_FOUND` for a run that does not exist, the store's own code for an error it throws as a `WorkflowError` (a `JsonFileStore` run file that cannot be read as a run, for one: `RESOURCE_FORMAT_INVALID`, `STATE_LEGACY_FORMAT` or `ENGINE_STORE_FAILED`, naming the file and its way out), and `ENGINE_STORE_FAILED` for any other, naming its cause (`Failed to load run from store: <its message>`). The run-file codes and their way out are added after version 0.47.0. Such a reply names no `run_phase`: no run was read.

`submitHumanResponse` takes `runId`, `gateId`, `choice`, and optionally, among others, `registry`, `respondedBy` and `caller`. `caller` is the call the expiry line names when an answer that comes after the question's time is up carries out its expiry: `submitHumanResponse` (the default), `submit_human_response`, `respond`, `run` or `agent`; any other value rejects as above (added after version 0.46.0).

Each of these functions, and `executeEngineStep`, `advanceRun`, `drainFinalizers`, `abandonRun`, `reclaimStep` and `getWorkflowForRun`, checks the parts it takes before anything is read or written: the store (present); the definition (an object whose `steps` is an object); the options object (`getWorkflowForRun`'s `opts`; `reclaimStep`'s `options`, when given, an object); each part it requires (`runId`, `command`, `step`, `stepName`, `gateId`, `choice`, `retryVerb` and `verb` strings; `input` present and not `null`; `run` a run record; `dispatcher` a function when the step needs one); and each optional one it was given (`registry` an extension registry, whose `getHandler`, `getAdapter`, `getOrCreateRateLimiter` and `has` are functions; `dispatcher` a function; `onStep` and the other callbacks functions; `stepMeta` and `traceBufferStore` objects; `trace` an array; `writerNonce`, `respondedBy`, `claimToken`, `command` and `reason` strings; `terminalOk` a boolean; `outputSource` one of its values). An options object may hold only the members its type has: any other is refused as not an option of the function, so an options object written for another version is refused, not ignored. An optional member left out takes its default; given as `null`, it is refused. A missing or wrong-typed part rejects with a `WorkflowError` with the code `VALIDATION_OPTION_INVALID`, naming every such part at once with what it must be and the type it was given, never its value, for example `executeStep was called with 2 invalid option(s): options.runId must be a string (got undefined); options.now must be a valid Date (got string). Nothing was read or written.` Two limits to "at once": a store, registry, driver or caller that an earlier check refuses is named first, alone (a registry or store of another release, a malformed driver and an unknown caller under their own codes); and a missing dispatcher is named once the definition and `command` are sound. Added after version 0.47.0.

### `driver`

`executeStep`, `executeChain`, `submitHumanResponse` and `advanceRun` take an optional `driver`, your program's name: `{ by, by_source, channel }`.

| Field       | Takes                                                                                                                                             |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `by`        | The name: text of 1 to 200 characters, not only spaces, with no control character.                                                                |
| `by_source` | How the name is known: `stated` (your program says it), `ambient` (from the environment, as `REALM_OPERATOR` is) or `derived` (from the OS user). |
| `channel`   | Your own word for the way the call came in: 1 to 64 characters of `a`–`z`, `0`–`9`, `_` and `-`, such as `cron`.                                  |

With any other value the call rejects with a `WorkflowError` with the code `VALIDATION_ACTOR_INVALID` before anything is read or written, naming the field: for example `Invalid driver.by_source: not one of stated, ambient, derived.` or `Invalid driver.channel: not 1–64 characters of [a-z0-9_-].` `realm run inspect` shows a step's driver as `Taken by: <by> (as stated, via <channel>)`, `(from REALM_OPERATOR, via <channel>)` or `(from the OS user, via <channel>)`.

## The stores Realm ships

| Class                      | Package                       | Keeps                                                                                       | Built with                                                                                               |
| -------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| The Realm home             | `@sensigo/realm-store-sqlite` | Runs, workflows, failed attempts, trace entries, replays and dedup marks, in one `realm.db` | `openRealmHome({ home? })`; for an MCP host, `createRealmMcpServerOnHome` from `@sensigo/realm-mcp/home` |
| `InMemoryTraceBufferStore` | `@sensigo/realm`              | Trace entries, in memory.                                                                   | `new InMemoryTraceBufferStore(runStore)`.                                                                |
| `InMemoryStore`            | `@sensigo/realm-testing`      | Runs, in memory.                                                                            | `new InMemoryStore()`.                                                                                   |

The JSON file stores (`JsonFileStore`, `JsonWorkflowStore`, `JsonFileFailedAttemptStore`, `JsonTraceBufferStore`) are not how Realm keeps its data: a Realm home's fences refuse them.

`JsonFileStore` and `InMemoryStore` each have a `clock`: the time they stamp their writes with (added after version 0.48.0). `JsonFileStore` takes no clock: its clock is this computer's, or the clock file of a [test location](environment-and-files.md#the-clock-a-runs-times-come-from) when its folder is one. `InMemoryStore` takes one, `new InMemoryStore({ clock })`, and uses `systemClock` when none is given. Each `create`, `update` and `claimStep` reads the clock once and stamps everything it records with that reading: `created_at`, `updated_at`, and a claim's `since` and deadline. The clock does not stamp times taken outside the store, or durations. `settleStep` reads it once too, inside its write, and every time it records comes from that reading: `updated_at`, a gate's `opened_at` and `expires_at`, an ended run's `abandoned_at`. A read takes one reading before it loads: `get` returns `{ record, at }`, and `list` returns `{ snapshots, read_at, consistent_snapshot }`, each record with the reading it is judged at. `stampSeal` does not read the clock.

`JsonFileStore` has a `runsDirPath` property with its folder, and `listWithDiagnostics(workflowId?)`, which returns `{ snapshots, read_at, consistent_snapshot, unreadable, copies }`: every readable run, as `list` returns it, and each run file it cannot read as a run (empty, not JSON, not a run record, holding another run, in the format of an earlier Realm, or not readable), with its `file`, `path`, `class`, the reason and the way out (added after version 0.47.0). A copy of a run whose own file reads (see `isCopyOfReadableRun`) is in `copies`, not `unreadable`. `workflowId` filters `snapshots` only: every damaged file is reported whatever the filter, since what it holds cannot be trusted. Its `get` refuses such a file, and `list` every such file but a copy of a run whose own file reads, with its typed error: `RESOURCE_FORMAT_INVALID`, `STATE_LEGACY_FORMAT` or `ENGINE_STORE_FAILED`, naming the file and its way out. `list(workflowId)` and `reconcileKeys(workflowId)` refuse only a damaged file that can concern that workflow (see `damagedFileConcerns`). A runs folder that cannot be read or made is refused with `ENGINE_STORE_FAILED`, naming the folder. Up to version 0.47.0, `list` returned a file that was JSON but not a run, or in the format of an earlier Realm, and `get` returned a file holding another run.

## The run store interface

A run store implements `RunStore`. It has 3 properties, 6 functions every store must have, and 1 optional function. Every function that reads or writes a run returns the reading of the store's clock it used, with the record (added after version 0.48.0).

| Member                                        | Required | What it must do                                                                                                                                                                                                                                                                 |
| --------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `persistsClaims`                              | Yes      | `true` if the store keeps a record's `claims` field. With `false`, `realm run reclaim` reports that it cannot work, and does nothing.                                                                                                                                           |
| `persistedRunRecordFields`                    | No       | The set of [record fields](#persistedrunrecordfields) the store keeps unchanged.                                                                                                                                                                                                |
| `clock`                                       | Yes      | The [`Clock`](#a-stores-clock) the store reads the time from. Realm refuses a store without one with `VALIDATION_OPTION_INVALID`, naming `store.clock`.                                                                                                                         |
| `create(options)`                             | Yes      | Make a run and return `{ record, at, created: true }`, `at` the reading the run is stamped with. With an idempotency key that matches a run, apply the [policy](#createoptions) for it; a run it returns is `{ record, at, created: false }`.                                   |
| `get(runId)`                                  | Yes      | Read the clock once, then the record, and return `{ record, at }`: `at` is the reading, raised to the record's own `updated_at` when that is later by at most 5 seconds (see `floorAtRecord`). If there is none, throw a `WorkflowError` with the code `STATE_RUN_NOT_FOUND`.   |
| `update(record)`                              | Yes      | Write the record if its `version` equals the stored one, add 1 to the version, and return `{ record, at }`. Otherwise throw `STATE_SNAPSHOT_MISMATCH`.                                                                                                                          |
| `list(workflowId?)`                           | Yes      | Read the clock once, then every record, or those of one workflow, and return `{ snapshots, read_at, consistent_snapshot }`: each record as `get` returns it, the reading, and whether every record was read in one pass.                                                        |
| `claimStep(runId, stepName, definition)`      | Yes      | As one atomic act: read the record afresh, check that the step is not started or settled and can still run, add it to `in_progress_steps`, add 1 to the version, write, and return `{ record, at }`. Throw `STATE_STEP_ALREADY_CLAIMED` or `STATE_STEP_NOT_ELIGIBLE` otherwise. |
| `settleStep(runId, delta, definition?)`       | Yes      | As one atomic act: read the record afresh, apply one settlement to it, write. See [`settleStep`](#settlestep). Realm refuses a store without it with `VALIDATION_OPTION_INVALID`, naming `store.settleStep`.                                                                    |
| `stampSeal(runId, sealedBy, expectedVersion)` | No       | Write how an ended run ended onto a record that lacks it. Used by `realm run migrate --stamp-seals`, which refuses a store without it.                                                                                                                                          |

Of 2 `claimStep` calls for the same step made at the same time, from any process on any machine that shares the store, exactly 1 must succeed. Everything that keeps a step from running twice rests on this.

The file store's two errors, as a caller sees them:

```json
{ "code": "STATE_RUN_NOT_FOUND", "message": "Run not found: nope" }
{ "code": "STATE_SNAPSHOT_MISMATCH", "message": "Version conflict — run was modified by another process" }
```

### `create(options)`

| Option            | Required | Holds                                                                                                                                                                             |
| ----------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `workflowId`      | Yes      | The workflow's ID.                                                                                                                                                                |
| `workflowVersion` | Yes      | The workflow's version.                                                                                                                                                           |
| `params`          | Yes      | The run's parameters.                                                                                                                                                             |
| `idempotencyKey`  | No       | A key. A second `create` with the same workflow and key finds the first run.                                                                                                      |
| `onLiveMatch`     | No       | What to do when the key matches an open run: `use_existing` (the default) returns it with `created: false`; `fail` throws `STATE_RUN_ALREADY_ACTIVE`.                             |
| `onTerminalMatch` | No       | What to do when the key matches an ended run: `reuse` (the default), `reject`, `rerun_if_failed` or `rerun`. See [Idempotency and batches](../guides/idempotency-and-batches.md). |
| `parentRunId`     | No       | The run that started this one.                                                                                                                                                    |

A new run has `version` 0 and the phase `running`.

### `persistedRunRecordFields`

A store that keeps the whole record, as the file store does, lists all 8 fields. A store that maps a record onto columns lists only the fields it has columns for. For a field that is not listed, Realm does not trust an empty value, and says so.

| Field                        | If the store loses it                                                                      |
| ---------------------------- | ------------------------------------------------------------------------------------------ |
| `capability_blocks`          | A step that is blocked looks free.                                                         |
| `workflow_context_snapshots` | The history of the workflow's context files is lost.                                       |
| `extension_identity`         | A change in the project's code can never be detected.                                      |
| `validation_rejections`      | A step whose answers keep being refused is never stopped.                                  |
| `defaulted_steps`            | The run no longer lists the steps that were given their default output.                    |
| `settled`                    | `settleStep` cannot tell what was already settled. A store with `settleStep` must list it. |
| `finalizer_ledger`           | Cleanup steps may run twice, or not at all. A store with `settleStep` must list it.        |
| `sealed_by`                  | Readers get the wrong answer to how the run ended. A store with `settleStep` must list it. |

With a store that lists no fields, `get_run_state` warned:

```text
this run store does not persist 'capability_blocks' — capability-block state is unavailable and not authoritative (an empty result may mean "no blocks" or "this store cannot report blocks at all").
```

### `settleStep`

`settleStep` applies one change to a run under the store's own lock: a step's result, a gate opened or answered, a cleanup step taken or done. Realm gives the change as data, and the store applies it with the function `applySettlement`, which `@sensigo/realm` exports.

| Rule                                                                                                                                                                                                                                            |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Read the record inside the lock. Do not use a record the caller read earlier.                                                                                                                                                                   |
| Read the store's clock once, inside the lock: `takeReading(clock, record, delta)`. Pass the reading as `applySettlement`'s option `at`, and return it as the result's `at`. Every time the change records comes from it, `updated_at` included. |
| Return `{ applied: false, reason, run, at }` when `applySettlement` refuses the change. Do not throw.                                                                                                                                           |
| Throw `STATE_SNAPSHOT_MISMATCH` when `applySettlement` refuses a `seal_run` change as `moved`: the run changed after the caller read it.                                                                                                        |
| Throw when the store itself fails: it cannot be reached, or the lock cannot be taken.                                                                                                                                                           |
| Throw for a kind of change the store does not know. Do not ignore it.                                                                                                                                                                           |
| Make the read, the change and the write one atomic act, however many statements that takes.                                                                                                                                                     |
| Call `applySettlement` with the option `cascadeGuards: true`.                                                                                                                                                                                   |
| Take no `definition` for a `seal_run` change: a run is sealed even when its workflow is gone. Every other change comes with one.                                                                                                                |

With `cascadeGuards: true`, a change that makes a guard step ready also decides that guard, and any guard that one makes ready, in the record `applySettlement` returns. The store writes that record once. The result lists the guards in `guards`. A guard whose `when` or `abort_unless` cannot be evaluated is recorded as failed, and the change still applies. Without the option, `applySettlement` decides no guard, and throws on such a guard. Only a store's own `settleStep` sets the option on a write: Realm's callers pass the store the change and read `guards` from what it returns. The contract's laws `GUARD_CASCADE_ONE_WRITE` and `GUARD_CASCADE_TOTAL` check it.

### A store's clock

A `Clock` has two functions: `now()`, which returns the current time as a new `Date`, and `at(when, fn)`, which runs `fn` once when the clock reaches `when` and returns a function that cancels it.

`createSystemClock({ onWaiterError })` builds a clock on this computer's time. A function given to `at` that throws or rejects is passed to `onWaiterError`, and a forward step of the computer's clock is noticed within 60 seconds. `systemClock` is the clock a store uses when it is given none. Its `at` works as `createSystemClock`'s does, and passes a failure to the program's sink, which it reads when the function fails: `setClockErrorSink(sink)` sets the sink, once, when the program starts, and `clockErrorSink()` returns it (added after version 0.48.0, whose `systemClock` threw from `at`). With no sink set, the failure is thrown again as an uncaught exception, never dropped. The `realm` command and the `realm-mcp` server each set a sink that prints the error's message on standard error.

The clock of a store opened at a [test location](environment-and-files.md#the-clock-a-runs-times-come-from) runs a function given to `at` when the time in the location's clock file reaches `when`, in any program that has the store open: it watches the file's folder, and reads the file every 100 milliseconds while a function waits. When the file cannot be read 50 times in a row, every function waiting on it fails, and each failure goes to the program's sink (added after version 0.48.0).

`takeReading(clock, record?, delta?)` reads the clock once for a write. When the record's `updated_at` is ahead of the clock, the reading moves up to it, but by 5 seconds at most. With a settlement `delta`, it moves up to the latest `started_at` or `completed_at` of the evidence the delta carries too. `takeRawReading(clock)` reads the clock once, as a read does before it loads, and `floorAtRecord(reading, record)` moves that reading up to the record's `updated_at`, by 5 seconds at most, as `get` and `list` do for each record (added after version 0.48.0).

`floorAtHolder(reading, holderCreatedAt?)` moves a keyed `create`'s reading to 1 millisecond after the `created_at` of the run it replaces, again by 5 seconds at most. So a run started again under an idempotency key is stamped after the run it replaces when the clock stepped back by less than 5 seconds.

Every time Realm reads is one of five classes. A store's clock gives the first three; the last two never come from it. `CLOCK_READ_CLASSES` holds the five, with these words (added after version 0.48.0):

| Class      | The time                                                                                                                                                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `write`    | An instant a write records on the run (`updated_at`, a claim's deadline, an opened question's `opened_at`): the store's reading, taken once inside the write.                                                                        |
| `read`     | The instant every statement about a record a read returns is judged at (`as_of`): the store's reading, taken before the load.                                                                                                        |
| `event`    | An instant the engine records with what happened (a step's start and end, a drive failure, a guard's evidence): the store's clock, read where it happens.                                                                            |
| `outside`  | An instant compared with no instant the store's clock gave (a log line, a signature window, `Retry-After`, a price day, a request's start compared with another's): the host's clock, each read named in the census with its reason. |
| `duration` | A duration (elapsed time, a budget, a timeout): the monotonic clock, never compared with an instant.                                                                                                                                 |

Realm's own tests list every time its code reads, each under one class with its reason, and fail when a read is not listed. A reply's `as_of` is the instant every statement about time in the reply was judged at. It is not when the run last changed: two replies about a run that did not change carry different `as_of`s when they were judged at different times.

#### What a store's clock does not settle

- **More than one computer.** A store's clock is one computer's. A `JsonFileStore` on a folder that several computers share is not supported: each computer would stamp with its own clock.
- **A step of the computer's clock.** After the clock steps forward, every program judges every deadline early by the size of the step; after it steps back, late. When the clock steps back by up to 5 seconds, a write is stamped no earlier than the run's last change; after a longer step back, it is stamped 5 seconds after the clock, earlier than that change. A run started again under an idempotency key after the clock stepped back by exactly 5 seconds carries the same `created_at` as the run it replaces.
- **A test that fakes `Date`.** A `JsonFileStore` takes file locks, and the lock library judges a lock stale by the computer's clock. A test that fakes the global `Date` while another program uses the same store can make a held lock look stale, and that program takes it. Move a test location's clock instead.
- **Times outside a run.** A log line's time, a signature's time window, a `Retry-After` wait and the day a price applies come from this computer's clock, never the store's.
- **Durations.** How long a step, a request or a wait took is real elapsed time, never read from the store's clock.
- **Claims.** Whether a claim has lapsed is judged by its deadline against the reading of the program that judges it. Realm does not watch another program to see that it is still working.
- **Text rendered before this version.** A gate's message rendered with `from_now` before version 0.48.0 stays as it was written: it says the time from when it was rendered.
- **Reminders.** `realm run inspect` and `realm run list` show when a reminder is scheduled. Realm records no reminder as sent.
- **Drive failures written before this version.** They carry no evidence count or question id. The `drive_failing` finding judges such an entry by its time, and says so: `basis: legacy_stamp_order`.
- **A record stamped ahead.** A run whose last change is stamped more than 5 seconds after a reader's clock is reported with the finding `record_stamped_ahead`, not corrected, until a later write stamps it again. Such a run has no age yet: `realm run cleanup` does not select it until the clock passes its stamp.
- **A store of your own.** It is checked against these rules only when you run the [store contracts](testing-package.md#store-contracts) on it. Run them again after you upgrade Realm.

## The other store interfaces

| Interface              | Functions                                                                                                                                                                                                                   | Implemented by                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `TraceBufferStore`     | `append`, `read`, `delete`, `deleteAllForRun`, `statAllForRun`, `readAllForRun`. Optional: `appendFenced`, `deleteFenced`, `deleteAllForRunFenced`, `sealFenced`, `listSealedForRun`, and the property `traceCapabilities`. | `JsonTraceBufferStore`, `InMemoryTraceBufferStore`                    |
| `PerRunArtifactStore`  | `deleteAllForRun`, `statAllForRun`                                                                                                                                                                                          | `JsonFileStore`, `JsonFileFailedAttemptStore`, `JsonTraceBufferStore` |
| `OrphanSweepableStore` | `listOrphans`                                                                                                                                                                                                               | `JsonFileFailedAttemptStore`, `JsonTraceBufferStore`                  |
| `WorkflowRegistrar`    | `register`, `get`, `list`. Optional: `listWithDiagnostics`, `getCapped`.                                                                                                                                                    | `JsonWorkflowStore`                                                   |
| `FailedAttemptStore`   | `append`, `read`, `deleteAllForRun`, `statAllForRun`                                                                                                                                                                        | `JsonFileFailedAttemptStore`                                          |
| `DedupStore`           | `check`, `record`, `cleanup` (each returns a promise)                                                                                                                                                                       | the CLI's file and in-memory dedup stores                             |
| `ReplayStore`          | `save`, `get`                                                                                                                                                                                                               | the CLI's replay file store                                           |

`createRealmMcpServer` takes its failed-attempt store as any object with the functions `append`, `read` and `deleteAllForRun`.

Two rules hold for every store that deletes:

- A thing that is not there counts as deleted. A thing that cannot be reached must make the call fail. `realm run purge` reports a run as removed only because every store said so.
- `statAllForRun` must report the same number of bytes that `deleteAllForRun` then reports for an unchanged run.

The 3 fenced functions of a trace buffer take a condition on the run, and must check it and write as one atomic act. In version 0.45.0 they take a function that checks the run instead. A store that has one of them must have all 3.

## Check a store

`@sensigo/realm-testing` has a set of tests for each interface. Each takes your store and returns cases to run in your test framework. See [Store contracts](testing-package.md#store-contracts).

| For                                        | Contract                      |
| ------------------------------------------ | ----------------------------- |
| A run store                                | `runStoreFidelityContract`    |
| A run store's `settleStep` and `stampSeal` | `settlementContract`          |
| A store that deletes                       | `perRunArtifactStoreContract` |
| A trace buffer's fenced functions          | `fencedTraceBufferContract`   |

`runStoreFidelityContract` was run on 3 stores:

| Store                                                            | Cases | Failed |
| ---------------------------------------------------------------- | ----- | ------ |
| `InMemoryStore`                                                  | 23    | 0      |
| A copy that lists `capability_blocks` and drops it on `update`   | 23    | 1      |
| A copy that lists no fields and does not keep the identity entry | 15    | 0      |

The failure:

```text
FIDELITY_HONESTY — store declares persistedRunRecordFields includes 'capability_blocks' but a round-trip did NOT preserve it — the declared fidelity is DISHONEST (issue #188). …
```

The contracts run in one process. They cannot show that `claimStep` and `settleStep` are atomic across machines. A store shared by several machines needs its own test of that, against its real database.
